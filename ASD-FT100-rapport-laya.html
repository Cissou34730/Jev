Conclusion

Laya, dont la tête partagée est réentraînée sur les trois questions à la fois, domine toutes les autres configurations testées. Sur 503 tickets dont le problème n'a jamais été vu : 92,0 % sur service, 100 % sur remboursement et 80,2 % sur urgence, soit 90,7 % de décisions correctes.

L'effondrement observé lors de la première phase n'était pas une limite du modèle : il venait d'avoir entraîné une tête partagée sur une seule question. Entraînée sur les trois, elle les tient toutes. Les modèles de remplacement évalués entre-temps, MiniLM et mDeBERTa, restent nettement en dessous.

Le modèle est exporté en ONNX et compilé sans erreur par OpenVINO sur l'iGPU. Il est donc prêt à être servi et testé de bout en bout (§A).

Réserve essentielle : le jeu reste synthétique. Ce résultat démontre que l'architecture n'était pas le blocage et que la démarche est rationnelle ; il ne démontre pas encore que le modèle généralisera à de vrais tickets clients.

1.Objet

Évaluer des modèles de décision non génératifs, exécutables localement et exportables en ONNX/OpenVINO, pour classer des tickets de support. Le travail a commencé avec Laya, puis a comparé deux encodeurs NLI multilingues et plusieurs formes de spécialisation locale. Trois décisions sont mesurées par ticket :

QuestionTypeOptionsAttendu
servicechoice3facturation / technique / livraison
remboursementnoul2vrai / faux
urgencescore3 niveauxFaible / Modérée / Élevée

Le jeu de test est tickets-1000.json : 1000 tickets français, classes équilibrées (334 / 333 / 333).

L'objectif final n'est pas de gagner quelques points sur ce jeu synthétique, mais d'identifier le candidat le plus crédible pour un futur apprentissage supervisé sur des tickets métier réels.

3.Phase initiale — objectif Laya

Un seul objectif, formulé en une phrase : que service cesse de répondre technique à presque tout.

La question était ouverte sur le comment, et la démarche a consisté à éliminer les causes une par une, puis à agir sur celle qui restait. Trois hypothèses ont été posées successivement :

  1. le texte du prompt (instruction, descriptions des critères, libellés) oriente la décision ;
  2. le modèle est correctement entraîné mais mal lu, donc un réglage de décision suffit ;
  3. le chemin de décision lui-même est biaisé, et il faut le réentraîner.

Seule la troisième a survécu.

4.Démarche suivie sur Laya

  1. Établir une référence service en choice, sans aucun réglage : 50,5 % sur 200 tickets. Répartition des choix : technique 166, livraison 23, facturation 11 — pour une vérité de 68 / 60 / 72.
  2. Faire varier le texte du prompt Instruction reformulée, impérative, avec point d'interrogation : ±4 points sur 200, technique toujours dominant.
  3. Remplacer les descriptions des critères Charabia sur les trois critères : 37 %, technique 194/200. Puis « La recette du gateau au chocolat » comme description de technique : 50,5 %, technique 166/200 — identique à la référence.
  4. Renommer les libellés technique → B, etc. : 53 %, et la 2e option gagne toujours. Le mot n'est donc pas le pilote.
  5. Supprimer le ticket État constant sur 200 tickets : 34 %, chaque tête sort une classe fixe. Le texte du ticket n'est pas lu pour cette décision.
  6. Jouer sur la température 0,7 → 55,0 % ; 0,5 → 53,5 % ; contre 58,5 % à 1,0. Une température multiplie l'écart entre options, elle ne peut pas en privilégier une : ça dégrade.
  7. Instrumenter : journaliser les logits Sortie JSONL, une ligne par couple (ticket, question) avec les logits bruts, le biais et la température appliqués, les probabilités et l'argmax. C'est ce qui a rendu la suite mesurable.
  8. Ajouter un décalage par option Biais sur les logits avant softmax : 50,5 % → 58,5 % sur 200 ; 74,9 % sur 1000. Puis vérification sur une moitié tenue à l'écart : un seul chiffre suffit (T ≈ 5), les deux autres offsets n'apportent que 2–3 points.
  9. Convertir la question en noul Trois questions booléennes à la place du choice. Résultat : 132/128, 88/132, 155/140 contre la baseline triviale « toujours non ». Le biais suit la question, pas le type de question.
  10. Réentraîner la tête de décision seule Encodeur gelé, sortie mise en cache, objectif proper_reward fourni par Laya. Découpage par problème, parité vérifiée avant entraînement. Résultat en §7.

5.Échecs et impasses

Échec 1 — la description des critères est décorative

technique gagne 68 fois sur 68 avec « La recette du gateau au chocolat » comme description. Un modèle qui lit les critères ne peut pas faire ça. Trois essais concordants (charabia, recette, renommage).

Échec 2 — le libellé n'est pas le pilote

Renommé en B, la 2e option gagne toujours. Le prior est attaché à la position ou à la tête, pas au mot.

Échec 3 — l'exactitude sur jeu équilibré est trompeuse

Sur un jeu à 1/3–1/3–1/3, répartir ses réponses fait monter l'exactitude même sans lire le ticket. Le 58,5 % ne prouvait donc rien par lui-même, et le 74,9 % était ajusté sur les tickets qui le mesuraient.

Échec 4 — la conversion en noul n'a rien réglé

Le même prior apparaît sur la tête noul : technique à 193 true sur 200 pour 68 réels. Le problème a été déplacé, pas supprimé.

Échec 5 — le découpage « par tournure » ne découpait rien

Premier essai du split : 192 clés distinctes sur 200 tickets. Le générateur compose ouverture × problème × urgence × référence, donc presque chaque ticket est unique — découper au hasard. Détecté avant tout entraînement.

Échec 6 — deux défauts dans le script d'entraînement

La vérification de parité tournait avec le dropout actif (les deux forwards auraient divergé au hasard) ; et la séquence gel/dégel de l'encodeur était inversée, correcte par accident. Corrigés avant le premier lancement.

Échec 7 — modification d'un fichier pendant son exécution

train_head.py édité alors que l'entraînement tournait. Sans effet sur le run (Python lit le source une fois au démarrage), mais la pratique est fautive.

Correction identifiée — exécutée depuis (§10)

Entraîner les trois questions ensemble, pour que la tête partagée conserve les trois :

uv run python train_head.py --question service,remboursement,urgence

L'objectif proper_reward gère déjà les trois types — terme RPS pour score, binaire pour noul — et les 1000 tickets portent les trois valeurs attendues.

Cette correction n'a longtemps pas été lancée. Le projet est passé directement à l'évaluation de modèles de remplacement (§8 et §9), et c'est seulement après coup qu'elle a été exécutée. Son résultat, décisif, figure en §10.

8.Comparaison des modèles de remplacement

Après la phase Laya, deux modèles NLI multilingues non génératifs ont été évalués sur les mêmes 800 tickets tenus à l'écart. Les formulations des hypothèses ont été corrigées avant la comparaison ; la température n'a pas constitué un levier utile, car elle modifie la calibration sans corriger le classement des classes.

Les scores globaux sont presque identiques, mais ils masquent des comportements opposés. MiniLM est nettement meilleur sur service et environ huit fois plus rapide. mDeBERTa domine sur urgence, mais s'effondre sur service. Aucun des deux modèles zéro-shot ne constitue une solution générale fiable.

9.Spécialisation locale de MiniLM

Une tête linéaire distincte a été entraînée pour chaque décision sur les représentations d'un encodeur MiniLM gelé. Le découpage sépare des groupes de problèmes afin d'éviter de mesurer uniquement la mémorisation de formulations déjà vues. Les tailles des jeux de test spécialisés diffèrent du benchmark zéro-shot ; les écarts ci-dessous indiquent une tendance, pas une comparaison expérimentale parfaitement contrôlée.

Le résultat sur remboursement montre qu'un petit modèle peut apprendre efficacement une décision bien définie. À l'inverse, urgence reste faible : la classe « Modérée » est notamment presque absorbée par « Élevée ».

Fine-tuning partiel d'urgence — échec

Le dégel de la dernière couche de MiniLM n'a pas amélioré la généralisation : 50,5 % avec 648 exemples synthétiques supplémentaires et 46,0 % sans augmentation, contre 55,7 % avec la tête spécialisée et l'encodeur gelé. Ces checkpoints ne doivent pas être promus.

Ce que cette mesure corrige
  • L'effondrement n'était pas structurel. La tête partagée ne « perd » pas les autres questions : elle perd ce sur quoi on cesse de l'entraîner. Entraînée sur les trois, elle les tient toutes.
  • urgence avait bien du signal. Elle passe de 40,7 % à 79,1 %, alors que les phases précédentes concluaient à une absence de signal exploitable. C'est la plus forte progression des trois.
  • remboursement atteint 100 % sur des problèmes jamais vus, pour une base de 50,4 % en réponse constante. La compétence est réelle, et le réentraînement conjoint la renforce au lieu de la détruire.
Réserves sur ce run
  • Le modèle n'avait pas convergé. urgence gagnait encore près de 9 points entre la quinzième et la vingtième époque. C'est ce qui a motivé la continuation décrite en §10.2.
  • --save-best était actif, donc la moitié tenue à l'écart a aussi servi à choisir l'époque. Ici la meilleure époque est la dernière, ce qui annule en pratique l'effet de sélection, mais le chiffre reste une validation plutôt qu'un test strictement propre.
  • L'écart entre entraînement (94,97 %) et tenu à l'écart (90,26 %) était alors de 4,7 points : modéré, sans surapprentissage marqué.
  • Le jeu reste synthétique. Le découpage sépare les énoncés de problème, pas les clients ni les périodes.

10.2 Continuation de deux époques — où s'arrête le gain

L'entraînement a été repris à partir du checkpoint de l'époque 20, sans refaire les vingt premières, sur le même découpage et la même graine. L'état de l'optimiseur Adam n'étant pas conservé dans le checkpoint, la reprise repart avec un optimiseur neuf ; le taux d'apprentissage a donc été ramené de 1e-3 à 1e-4 pour éviter un à-coup à la reprise.

La lecture utile n'est pas seulement la colonne « Moyenne » mais la stabilité : les deux modèles zéro-shot et les deux premières phases de Laya gagnent sur une décision en perdant sur une autre. Seul Laya entraîné conjointement tient les trois simultanément, et il est le seul à franchir 90 % sur deux d'entre elles.

12.Décision technique

Candidat retenu — Laya, tête entraînée conjointement

Laya est retenu. Il est la seule configuration testée à tenir les trois décisions simultanément, et il devance les autres sur chacune d'elles prise isolément :

  • remboursement à 100 % sur des problèmes jamais vus, contre 92,8 % pour le meilleur concurrent ;
  • service à 92,0 %, contre 81,0 % ;
  • urgence à 80,2 %, contre 67,8 % pour le meilleur concurrent ;
  • entraînement réalisable sur CPU, encodeur gelé, environ 15 M de paramètres optimisés ;
  • chemin d'inférence déjà opérationnel : serveur OpenVINO et export ONNX existants.
Pourquoi la recommandation précédente était erronée

Une version antérieure de ce rapport désignait MiniLM. Cette recommandation reposait sur trois erreurs, corrigées ici :

  • le 99,4 % de Laya sur remboursement était décrit comme un artefact de distribution, alors que le jeu est équilibré à 496 / 504 et qu'une réponse constante plafonne à 50,4 % ;
  • urgence était déclaré sans signal exploitable, alors qu'il atteint 80,2 % une fois la tête correctement entraînée ;
  • le débit de MiniLM pesait dans l'arbitrage, alors qu'il est sans objet à 40 000 tickets par an.

Surtout, la comparaison a été menée avant d'avoir exécuté la correction déjà identifiée pour Laya. Les modèles de remplacement ont donc été opposés à une version volontairement dégradée du candidat initial.

MiniLM conserve un intérêt résiduel : il reste le plus léger et le plus rapide, et sa tête spécialisée atteint 92,8 % sur remboursement pour un coût d'entraînement très faible. C'est une solution de repli crédible si la taille du modèle devenait une contrainte de déploiement.

mDeBERTa n'a plus de rôle évident. Son seul avantage, urgence à 67,8 % en zéro-shot, est désormais dépassé de plus de douze points par Laya entraîné.

13.Limites et réserves

  • Le jeu de test vient d'un générateur. C'est la réserve la plus lourde de ce rapport. Le découpage sépare les énoncés de problème, mais tous les tickets partagent le vocabulaire, les tournures et la structure du même générateur. Laya peut avoir appris la grammaire du générateur autant que la tâche.
  • Le 90,7 % n'est pas un chiffre de production. Il est mesuré sur des problèmes jamais vus, ce qui est exigeant, mais à l'intérieur d'un univers synthétique.
  • Le surapprentissage a commencé. Entre 20 et 22 époques, l'écart entre entraînement et validation passe de 4,7 à 6,7 points pour 0,4 point de gain réel. Poursuivre sur ces données n'est plus rentable.
  • Il n'existe pas de jeu de test réellement indépendant. Les 503 tickets tenus à l'écart ont servi à suivre l'entraînement et à décider de s'arrêter : ce sont des données de validation, pas de test.
  • Le 100 % sur remboursement appelle de la prudence. Il peut signifier que la décision est explicitement présente dans le texte, mais aussi que le générateur y place des marqueurs trop réguliers.
  • Les protocoles ne sont pas strictement comparables d'une ligne à l'autre du tableau §11. Ils documentent une trajectoire expérimentale.
  • Aucune configuration n'atteint 95 % sur les trois décisions simultanément. Deux y sont pour Laya conjoint, mais urgence reste à 80,2 %.
  • Les chiffres viennent de l'évaluation PyTorch du script, pas du serveur. L'ONNX est vérifié numériquement (écart ~2e-05) et compile sous OpenVINO, mais la mesure de bout en bout n'a pas encore été faite.
  • Le 92,8 % historiquement observé côté client avec Laya sur 500 tickets est gonflé : environ la moitié a servi à l'entraînement. Toute mesure du client sur tickets-1000.json souffre du même biais.
  • La cohérence des budgets de séquence n'est pas vérifiée automatiquement : le chargement annonce max_len 1024, le serveur tourne à 256. Sans effet ici (~105 tokens en moyenne), mais à surveiller sur des tickets longs.

14.Suite recommandée

  1. Lancer le serveur et le client sur le checkpoint exporté (§A) pour vérifier que le chemin ONNX/OpenVINO reproduit les 90,7 % du script. C'est la seule étape encore immédiatement réalisable sur les données actuelles.
  2. Mesurer le checkpoint via le serveur sur tickets-503-laya-heldout.json. Le jeu tenu à l'écart est désormais exporté et permet une comparaison honnête avec l'évaluation PyTorch.
  3. Constituer un jeu de vrais tickets avec une définition stable et vérifiable de chaque décision. Sans cela, aucun des chiffres de ce rapport n'engage quoi que ce soit en production.
  4. Séparer entraînement, validation et test par client et par période, et non plus seulement par énoncé de problème, avec un jeu de test jamais consulté pendant l'entraînement.
  5. Mesurer la précision à couverture contrôlée : quelle proportion des tickets peut être décidée à 95 % de précision, en laissant le reste indécidé. C'est la métrique qui correspond réellement au besoin métier.
  6. Traiter urgence comme un problème à part : c'est la seule décision qui résiste encore, et il faut déterminer si le critère lui-même est défini de façon exploitable.
  7. Sur de vraies données, envisager de dégeler les dernières couches de l'encodeur. Jamais tenté ici, faute de GPU adapté, mais c'est le levier restant au-delà de la tête.
  8. Conserver MiniLM spécialisé comme repli léger, et abandonner mDeBERTa, désormais dominé sur ses trois questions.

A.Annexe — commandes

Tester soi-même le modèle retenu

Deux terminaux. Le premier sert le modèle, le second mesure.

# Terminal 1 — serveur
$env:LAYA_OV_ONNX_PATH = ".laya-cache\checkpoints\laya-head-joint-plus2\laya.onnx"
uv run python laya_serve_openvino.py --batch-states 50 --max-concurrent 1 --max-len 256
# Terminal 2 — client, une fois le serveur prêt
.\laya-client-spectre.ps1 -InputPath .\tickets-503-laya-heldout.json -BatchSize 50 -OutputPath .\resultats-client-heldout.json
Deux précautions
  • Ne pas passer --label-bias, ni -ScoreLowCut / -ScoreHighCut. Ces corrections ont été calées sur l'ancienne tête défaillante et fausseraient le résultat. Les valeurs par défaut sont les bonnes.
  • Le premier appel est lent : OpenVINO recompile le modèle pour l'iGPU après tout nouvel export. Attendre que le serveur annonce qu'il est prêt avant de lancer le client.

Recréer le jeu tenu à l'écart sans lancer d'entraînement

uv run python train_head.py --question service,remboursement,urgence --tickets tickets-1000.json --holdout 0.5 --seed 0 --heldout-out tickets-503-laya-heldout.json --split-only

Cette commande ne charge pas Laya et ne calcule pas l'encodeur. Elle reproduit exactement les 503 tickets utilisés pour les chiffres hors échantillon de ce rapport.

Entraîner la tête sur les trois questions

uv run python train_head.py --question service,remboursement,urgence --out .laya-cache/checkpoints/laya-head-joint --save-best

Sur Windows, forcer $env:PYTHONUTF8 = "1" : la console cp1252 ne peut pas encoder certains caractères du journal. Prévoir environ quinze minutes de mise en cache de l'encodeur avant la première époque.

Prolonger un entraînement existant

uv run python train_head.py --question service,remboursement,urgence --init .laya-cache/checkpoints/laya-head-joint --out .laya-cache/checkpoints/laya-head-joint-plus2 --epochs 2 --lr 1e-4

Le checkpoint ne contient que les poids : l'optimiseur repart de zéro, d'où le taux d'apprentissage réduit.

Exporter en ONNX

uv run python export_laya_master.py --repo .laya-cache/checkpoints/laya-head-joint-plus2 --out .laya-cache/checkpoints/laya-head-joint-plus2

L'export écrit laya.onnx et les fichiers de tokenizer à la racine du dossier, ce que le script d'entraînement ne fait pas ; le serveur en a besoin.

Évaluer MiniLM sous OpenVINO

uv run python test_minilm_nli.py --input tickets-800-minilm-validation.json --device GPU

Entraîner les têtes spécialisées MiniLM

uv run python train_minilm_heads.py
